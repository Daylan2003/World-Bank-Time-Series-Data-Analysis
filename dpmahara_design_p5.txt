ALTERNATIVES AND JUSTIFICATION

The main alternative design choice I made for this project was the way of how I represented my graph data structure. Initially, my choice was to use an adjacency matrix to represent my graph as this seemed simpler and easier to implement. However, I decided against this and made the choice to use an adjacency list. My justification for this is that it is much more efficient to update data in an adjacency list rather than an adjacency matrix. And since for this project we are dealing with are amount of data, I deemed this to be a good choice. 

Additionally, a second design alternative choice I made came when trying to figure out a way of how to traverse the graph. At first I was going to use the depth first search method, but decided it was a much better alternative to use Breadth first search to traverse my graph. My justification for this is that the graph is unweighted. Additionally, I am dealing with a lot of data, and a total of 266 countries. Therefore it is very likely that 2 countries have a direct relation to one another. Since the breadth first search algorithm checks the neighbours first, I deemed this to be the more efficient and better algorithm to use. 

Furthermore, a third design alternative I made was how I was storing a group of relations in my graph. The relations were tuples containing three elements each. I immediately saw two ways to store a group of these. The first was to use a linked list, but eventually I settled on using a vector as it required less overhead. Additionally, for this particular project I would not be deleting relations, so a linked list seemed unnecessary. That is my justification for using a vector to store my data.


RUNTIME ANALYSIS

The runtime for my ADJACENT command is O(m + log n). Searching for the target country in adjList takes O(log n) because adjList is a std::map, which is implemented as a balanced binary search tree. Usually it is implemented as a Red-Black tree where lookups take O(log n) time.  Inserting m adjacent countries into a std::set requires O(m log m) time since std::set is also a balanced binary search tree, making each insertion O(log m).  Finally, searching for each adjacent country’s name using double hashing takes O(m) in the worst case, as probing through the hash table may require up to O(1) per lookup for all m countries, hence, worst case of O(m). Since O(m log m) dominates O(m), the overall complexity simplifies to O(m + log n).
